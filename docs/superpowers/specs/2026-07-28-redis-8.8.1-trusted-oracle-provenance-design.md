## 1. 目的

本设计为 Kiwi 的 Redis 8.8.1 行为 Oracle 建立可审计、可重复、不能由自洽输入任意拼接的构建和运行证据。

正式 provenance 必须证明：

1. Primary build 和 verification rebuild 都来自 exact Redis 8.8.1 commit。
2. 两次构建使用同一受控命令、环境和可追溯工具链。
3. 两个独立 checkout 产生的 `redis-server` SHA-256 完全一致。
4. 正式 `INFO server` 身份来自 verification rebuild binary，不来自调用者指定的 primary binary。
5. 所有进程、进程组和临时目录清理成功后，provenance 才能原子发布。

本设计只服务 Cache OFF 兼容测试。它不构建、加载或发布 Embedded Redis Hot Tier，也不授权修改 `arana-db/redis` fork。

## 2. 为什么原有 metadata 自洽模型不够

以下输入均由调用者控制：

- Redis source path；
- primary `src/redis-server`；
- build metadata JSON；
- build log；
- metadata 中记录的 command、environment、hash 和 file identity。

Git 的普通 clean status 不列出 ignored 构建产物。调用者可以在 exact、clean Redis checkout 中放置一个 ignored 的伪造 `src/redis-server`，让它返回 `redis_version:8.8.1`，再生成与该 binary 和任意 build log 完全自洽的 metadata。

下列检查只能证明输入互相一致，不能证明 binary 的构建来源：

- metadata schema 正确；
- source HEAD 和 tag peeling 正确；
- binary/log path、SHA-256 和 device/inode 正确；
- command/environment 字段等于预期字符串；
- 运行的 binary 与已打开 binary FD 相同；
- `INFO server` 返回唯一的 `redis_version:8.8.1`。

因此 metadata 和 build log 只能作为审计记录，不能成为信任根。方案 A 通过 verifier 独立重建关闭该缺口。

## 3. 信任模型

### 3.1 不可信输入

- CLI 参数和调用者环境；
- ambient `PATH`；
- `PYTHONPATH`、`PYTHONHOME`、`PYTHONSTARTUP` 和用户 site packages；
- primary source working tree 中的 ignored artifacts；
- primary binary、build log 和 metadata；
- metadata 中声明的工具路径、版本、hash 和 command；
- output 路径及其父目录中的 symlink/path replacement。

### 3.2 当前信任根

- 当前 Kiwi commit 中经过 review 的 build/verifier controller；
- Linux kernel 提供的 file descriptor、`openat`、`O_NOFOLLOW`、`O_EXCL`、`stat` 和 `/proc/self/fd` 语义；
- 固定 Linux 系统解释器候选 `/usr/bin/python3`、`/bin/python3`；
- 受控目录 `/usr/bin:/bin` 中被打开、hash、identity 记录并通过 held FD 执行的 Git、CC 和 Make；
- Git 对 exact commit `77b6c308396c9700672390a210143a8496fb4b10` 的对象解析和 checkout；
- SHA-256 对当前威胁模型提供的内容等价证明。

系统 root、kernel、受控系统工具本身或 Git/SHA-256 基础设施被攻破不属于本任务防护范围。provenance 必须记录这些工具的 exact identity，以便外部供应链审计，而不是声称消除宿主机信任。

## 4. 总体数据流

```text
exact Redis source A
  → primary build controller
  → primary binary A + build log A + metadata A
                                  │
                                  ▼
                         verifier treats all as untrusted
                                  │
exact Git commit ──held Git FD──→ fresh disposable checkout B
                                  │
                                  ▼
                         controlled rebuild in B
                                  │
                                  ▼
                         verification binary B
                                  │
               SHA256(binary A) == SHA256(binary B)?
                         │ yes                 │ no
                         ▼                     ▼
             run binary B for INFO       fail, no provenance
                         │
                         ▼
              stop/reap process group
                         │
                         ▼
       remove runtime + checkout B + verify cleanup
                         │
                         ▼
       recheck held identities/hashes and output parent
                         │
                         ▼
             atomically publish provenance v2
```

正式消费者只接受 provenance v2。它不能把 primary binary endpoint、裸 Redis endpoint 或 build metadata 直接当作发布证据。

## 5. 受控 bootstrap

两个 shell 入口必须在执行 Python 代码之前建立最小信任边界：

1. 不调用 ambient `command -v python3` 或 ambient `realpath`。
2. 只按顺序检查 `/usr/bin/python3`、`/bin/python3` 是否为可执行文件。
3. 使用 shell builtin 清理 `PYTHONPATH`、`PYTHONHOME`、`PYTHONSTARTUP`、`PYTHONUSERBASE`。
4. 固定 `PATH=/usr/bin:/bin`、`LC_ALL=C`、`LANG=C`。
5. 使用 `python3 -I -E -s` 启动 controller。
6. Python 启动后打开并记录实际 interpreter executable 的路径、版本、SHA-256 和 file identity；两个阶段必须使用同一受控解释器 identity。

固定系统路径是当前 Linux/WSL Oracle 运行环境的显式前置条件。其他布局必须明确 FAIL，不得回退 ambient PATH。

## 6. 受控外部工具

Git、CC 和 Make 必须统一遵循：

1. 只从 `/usr/bin:/bin` 解析。
2. 拒绝非 regular file、不可执行文件和不允许的路径布局。
3. 打开只读 FD，记录 resolved path、版本、SHA-256、device、inode、mode、size 和 link count。
4. 所有执行通过 `/proc/self/fd/<fd>` 和 `pass_fds` 绑定 held executable。
5. 执行前后复核 path 与 held FD identity；路径被替换时 FAIL，不能悄悄执行新文件。
6. 短命令使用 monotonic absolute deadline、stdout/stderr cap、独立 process group、TERM grace、KILL 和 wait/reap。

Local Git config 查询也必须走同一 bounded held-FD runner。合法 exit code `0` 和 `1` 由调用方解释，runner 不能用无界 `subprocess.run` 回退。

真正的 Redis build 必须通过 held Make FD 执行；只用 held FD探测 `make --version`、随后按路径执行 build 不满足设计。

## 7. Primary build

Primary build controller 负责产生审计输入，不负责给自己授信。

### 7.1 前置检查

- source 是真实目录，不是 symlink；
- `.git` identity 在整个生命周期被 held FD 绑定；
- HEAD 和 `8.8.1^{}` 都等于 exact commit；
- `core.worktree`、replace objects、alternates、risky Git booleans 等配置 fail closed；
- tracked/untracked 状态干净；
- build 前不允许任何 Redis build artifact；
- metadata 和 build log 使用不可覆盖、安全父目录和 `O_EXCL` 新建。

### 7.2 固定构建合同

```text
make -C /proc/self/fd/<source_fd>
  BUILD_TLS=no
  MALLOC=libc
  -j 1
  redis-server
```

环境只包含批准白名单，包括固定 locale、受控 `PATH`、held compiler path 和可重复构建需要的确定性变量。`SOURCE_DATE_EPOCH` 必须由 exact commit object 确定并记录，不能取当前时间。

### 7.3 Primary metadata v2

`kiwi-redis-oracle-build/v2` 的顶层 key set 固定为：

| 字段 | 类型 | 必选 | 合同 |
|---|---|---|---|
| `schema_version` | string | 是 | 必须等于 `kiwi-redis-oracle-build/v2` |
| `controller` | object | 是 | `kiwi_commit`、`script`、`python` |
| `source` | object | 是 | exact Redis repository、tag、commit、HEAD、tag peeling、source root 和 Git directory identity |
| `toolchain` | object | 是 | `git`、`cc`、`make` 和 `transitive_tools`；所有实际执行工具均需进入证据 |
| `recipe` | object | 是 | versioned recipe ID、semantic/executed argv、semantic/executed environment、HOME/TMPDIR identity、`SOURCE_DATE_EPOCH` 和 jobs |
| `primary_build` | object | 是 | 时间、exit code、build log、binary、构建前后 artifact manifest |

嵌套对象固定如下；没有 optional key：

| 对象 | 精确字段 |
|---|---|
| `controller` | `kiwi_commit: hex40`、`script: file_evidence`、`python: tool_evidence` |
| `source` | `repository: string`、`tag: string`、`commit: hex40`、`head: hex40`、`tag_commit: hex40`、`root: directory_evidence`、`git_dir: directory_evidence`、`tracked_untracked_clean: bool` |
| `toolchain` | `git: tool_evidence`、`cc: tool_evidence`、`make: tool_evidence`、`transitive_tools: array<{role: string, evidence: tool_evidence}>`，按 role/path 排序且无重复 |
| `recipe` | `id: string`、`semantic_argv: string[]`、`executed_argv: string[]`、`semantic_environment: map<string,string>`、`executed_environment: map<string,string>`、`home: directory_evidence`、`tmpdir: directory_evidence`、`source_date_epoch: u64`、`jobs: u16` |
| `primary_build` | `started_at_utc: RFC3339 string`、`finished_at_utc: RFC3339 string`、`exit_code: i32`、`log: file_evidence`、`binary: file_evidence`、`pre_build_artifacts: artifact_manifest`、`post_build_artifacts: artifact_manifest` |
| `file_evidence` | `path: absolute UTF-8 string`、`sha256: lower_hex64`、`identity: file_identity` |
| `tool_evidence` | `path: absolute UTF-8 string`、`version: string`、`sha256: lower_hex64`、`identity: file_identity` |
| `directory_evidence` | `path: absolute UTF-8 string`、`identity: file_identity` |
| `file_identity` | `device: u64`、`inode: u64`、`mode: u32`、`size: u64`、`nlink: u64` |
| `artifact_manifest` | array of `{path: source-relative UTF-8 string, kind: string, size: u64, sha256: lower_hex64}`；`kind` 必须等于 `regular`，按 path 字节序升序，无重复 |

固定值和边界：

- `source.repository=https://github.com/redis/redis.git`、`tag=8.8.1`，`commit=head=tag_commit=77b6c308396c9700672390a210143a8496fb4b10`；
- `recipe.id=redis-8.8.1-oracle-build/v2`、`source_date_epoch=1784834134`、`jobs=1`；
- `recipe.semantic_argv` 精确等于 `make -C /proc/self/fd/{source_fd} BUILD_TLS=no MALLOC=libc -j 1 redis-server` 的结构化模板；`recipe.executed_argv` 保存实际数值 FD，且除 `{source_fd}` 替换外必须逐项等于 semantic argv；不保存 shell command string；
- `recipe.semantic_environment` 的精确 key/value 是：`PATH=/usr/bin:/bin`、`LC_ALL=C`、`LANG=C`、`TZ=UTC`、`SOURCE_DATE_EPOCH=1784834134`、`HOME={private_home}`、`TMPDIR={private_tmpdir}`、`CC=/proc/self/fd/{cc_fd}`、`AR=/proc/self/fd/{ar_fd}`、`RANLIB=/proc/self/fd/{ranlib_fd}`、`SHELL=/proc/self/fd/{sh_fd}`；
- `recipe.executed_environment` 必须只有同一组 key，并把 `private_home`、`private_tmpdir`、`cc_fd`、`ar_fd`、`ranlib_fd`、`sh_fd` placeholder替换为本次实际值；`HOME`、`TMPDIR` 分别等于 `recipe.home.path`、`recipe.tmpdir.path`。禁止任何 `PYTHON*`、额外 `GIT_*`、代理变量、用户配置或 metadata 提供的 executable path；
- `toolchain.transitive_tools` 至少包含 role `ar`、`ranlib`、`sh`、`cc-assembler` 和 `cc-linker`；真实 build 观察到的其他 executable 必须以唯一 role/path 加入。所有项都从受控边界解析并记录，不能因未列入顶层 `git/cc/make` 而省略；
- metadata UTF-8 编码后不得超过 1 MiB；任一 string 不得含 NUL，path 最大 4096 bytes，version 最大 16 KiB，其他 string 最大 4096 bytes，每个 argv 最多 32 项，environment 最多 32 项，artifact manifest 最多 4096 项，transitive tools 最多 64 项；
- Artifact manifest 的扫描集合固定为 `git -C {source} ls-files --others --ignored --exclude-standard -z` 返回的全部 path；每项必须是 source root 内的 regular file，不允许 symlink、device、socket 或越界 path。Build 前 manifest 必须为空；build 后记录完整集合。Primary 和 verification rebuild 的 post-build manifest 必须在相对 path、kind、size、SHA-256 上逐项相等；
- `started_at_utc <= finished_at_utc`、`exit_code=0`；
- `recipe.home` 和 `recipe.tmpdir` 是 primary 私有目录，权限为 `0700`，不能与 verification rebuild 对应目录共享 path、identity 或内容；构建前后都必须为空，否则构建失败；
- JSON parser 必须拒绝 duplicate key、未知 key、未知 schema、类型漂移、超限输入和非规范 SHA/commit。

metadata 的作用是审计和后续交叉核对。即使全部字段正确，也不能跳过 verification rebuild。

## 8. Verification rebuild

### 8.1 Fresh checkout

Verifier 在新建的私有 runtime root 中创建独立 checkout B：

- runtime root 和 checkout leaf 使用安全父目录、不可预测名称和 restrictive permissions；
- 当前唯一批准的 clone primitive 是通过 held Git FD 执行 `git clone --local --no-hardlinks --no-checkout /proc/self/fd/{source_fd} {checkout_b}`，随后在 checkout B 中 detached checkout exact commit；
- 独立验证 clone B 的 HEAD、tag peeling、Git layout、risky config 和 clean status；
- clone B 在 build 前必须没有 ignored Redis build artifact；
- checkout B 与 source A 不能共享 working tree 文件、binary、build log 或 metadata。

Clone runner 使用空白环境加批准白名单，设置 `GIT_CONFIG_NOSYSTEM=1`、`GIT_CONFIG_GLOBAL=/dev/null`、`GIT_CONFIG_SYSTEM=/dev/null`，并禁止其他 ambient `GIT_*`。Clone 前后必须复核 source FD 与 source path identity；测试中把 caller path rename-replace 后，clone 只能从 held FD 的原目录成功或明确失败，不能访问 replacement marker。

Clone 完成后必须确认：checkout B 没有 `objects/info/alternates`；source A 和 checkout B 的所有 regular working-tree/Git object 文件不存在相同 `(device,inode)`；checkout B 不引用 primary binary、metadata 或 log；两边 source root、Git directory 和 private HOME identity 均不同。

实施 task 的第一个 Linux 硬门禁必须在真实 Redis 8.8.1 exact checkout 上验证上述 exact primitive。若当前 Git/WSL 不支持该 `/proc/self/fd` clone，task 标记 BLOCKED，并回到规划 task决定新的唯一 primitive；实施者不得自行改用 caller path、hardlink clone、alternates、shared object store 或另一套未批准 transfer。

### 8.2 Independent build

Verifier 使用自己解析和持有的 Python、Git、CC 和 Make，以与 primary build 完全相同的 argv 和环境在 checkout B 中构建。

Primary 和 verification rebuild 必须使用两个分别新建、权限为 `0700`、构建前后均为空的私有 HOME。两者 path 和 identity 必须不同；任何一方写入 HOME 都必须 FAIL。未来若批准 compiler cache，它必须作为单独 Decision 和 versioned recipe 输入，不能隐式复用 HOME/cache 状态。

构建结束后必须：

- 复核 checkout B exact/clean 状态；
- 按 §7.3 的固定扫描规则记录完整 post-build artifact manifest，并要求它与 primary manifest逐项相等；
- 打开 verification binary B 和 build log B；
- 计算并记录 hash/identity；
- 要求 `SHA256(binary A) == SHA256(binary B)`。

如果两个受控独立 checkout 的 binary 不一致，verifier 必须失败。实施 task 应先调查路径、时间、locale、toolchain 或 nondeterministic build 输入，不能把比较降级为版本、size、symbols 或部分 hash。

## 9. Runtime identity

正式 runtime evidence 只运行 verification binary B：

- 通过 held binary FD 启动；
- 使用 private runtime directory、loopback 和动态端口；
- 禁止 daemonize、持久化和外部配置继承；
- INFO probe 有 absolute deadline、frame/output limits 和严格 RESP parsing；
- `INFO server` 必须恰好出现一个 `redis_version`，值为 `8.8.1`；
- 进程提前退出、额外版本值、partial response、timeout 或 output cap 均 FAIL。

Primary binary A 不作为正式运行对象。这样即使调用者提供任意可响应 8.8.1 的 fake binary，也无法进入 provenance。

## 10. Cleanup-before-publish

成功顺序固定为：

1. 构造内存中的 provenance candidate。
2. TERM/KILL/wait 回收 Redis process group。
3. 确认没有属于本次验证的存活进程。
4. 删除 runtime data。
5. 删除 fresh checkout B 和 verification build log。
6. 确认临时根目录清理成功。
7. 重新核验 primary metadata、primary binary、primary log、source A、tool FDs 和 output parent identity/hash。
8. 关闭不再需要的 fallible evidence handles。
9. 使用不可覆盖、no-follow、同目录临时文件和原子 link/rename 语义发布 provenance。
10. 发布后只允许 no-throw cleanup。

任一 fallible cleanup 失败时，最终 provenance 必须不存在。普通 process group 不宣称能约束主动 `setsid()` 逃逸的任意恶意 binary；正式运行对象是 independent exact rebuild，从输入模型中移除了任意 binary。

## 11. Provenance v2

`kiwi-redis-oracle-provenance/v2` 的顶层 key set 固定为：

| 字段 | 类型 | 必选 | 精确字段 |
|---|---|---|---|
| `schema_version` | string | 是 | 必须等于 `kiwi-redis-oracle-provenance/v2` |
| `controller` | object | 是 | 与 metadata `controller` 同结构，内容为 verifier controller |
| `redis` | object | 是 | `repository`、`tag`、`commit` |
| `primary_build` | object | 是 | `metadata: file_evidence`、`source`、`toolchain`、`recipe`、`started_at_utc`、`finished_at_utc`、`exit_code`、`log`、`binary`、`pre_build_artifacts`、`post_build_artifacts` |
| `verification_rebuild` | object | 是 | `clone_method`、`source`、`toolchain`、`recipe`、`started_at_utc`、`finished_at_utc`、`exit_code`、`log`、`binary`、`pre_build_artifacts`、`post_build_artifacts` |
| `comparison` | object | 是 | `algorithm`、`primary_binary_sha256`、`verification_binary_sha256`、`binary_hash_equal`、`artifact_manifests_equal` |
| `runtime` | object | 是 | `binary_sha256`、`binary_identity`、`info_server_sha256`、`redis_version`、`started_at_utc`、`stopped_at_utc`、`exit_code` |
| `cleanup` | object | 是 | `redis_process_reaped`、`runtime_removed`、`checkout_removed`、`verification_log_removed`、`temporary_root_removed`、`primary_evidence_revalidated`、`source_revalidated`、`tool_fds_revalidated`、`output_parent_revalidated`、`evidence_handles_closed`、`completed_at_utc` |
| `platform` | object | 是 | `os`、`kernel`、`architecture`、`wsl_distribution` |
| `limitations` | string[] | 是 | threat-model 明确排除项，最多 16 项，每项最多 4096 bytes |

`source`、`toolchain`、`recipe`、`file_evidence`、`file_identity` 和所有字符串/集合/总 JSON 大小限制沿用 metadata v2；provenance UTF-8 编码后也不得超过 1 MiB。`verification_rebuild.clone_method` 必须等于 `git-local-no-hardlinks-procfd/v1`。`wsl_distribution` 在原生 Linux 上使用空字符串，不允许省略字段。

必须同时满足以下跨字段不变量：

1. `redis`、`primary_build.source` 和 `verification_rebuild.source` 的 repository/tag/commit/head/tag_commit 都是固定 Redis 8.8.1 identity。
2. `primary_build.metadata.sha256` 是实际输入 metadata bytes 的 hash；metadata strict parse 后，其 source、toolchain、recipe、started/finished time、exit code、log、binary 和 pre/post artifact manifest 必须逐字段等于 provenance 的 `primary_build`。
3. Primary 和 verification recipe 的 ID、semantic argv/environment、source epoch 和 jobs 相等；executed argv/environment 只允许 FD、HOME 和 TMPDIR实际值不同。两组 private HOME/TMPDIR 都构建前后为空且 identity 不同。
4. `comparison.algorithm=sha256`，两个 hash 分别等于对应 binary evidence，`binary_hash_equal=true`，且两边 post-build artifact manifest 逐项相等并令 `artifact_manifests_equal=true`。
5. `runtime.binary_sha256=verification_rebuild.binary.sha256`，`runtime.binary_identity=verification_rebuild.binary.identity`，不能绑定 primary binary。
6. `runtime.redis_version=8.8.1`，`info_server_sha256` 来自严格解析前的 bounded raw bytes。
7. 所有 start/end timestamp 有序；两个 build 和 runtime `exit_code=0`。
8. `cleanup` 的十个 boolean 全部为 `true`：Redis process 已回收，runtime、checkout B、verification log 和 temporary root 已删除，primary evidence、source A、tool FDs 和 output parent 已完成最终复核，不再需要的 fallible evidence handles 已成功关闭；`cleanup.completed_at_utc` 不早于 runtime stop 和 rebuild finish，且最终 output 在该时间之后才原子发布。
9. Shell 和 PowerShell 两入口的 stable evidence projection 必须逐字段相同：schema；Redis repository/tag/commit；primary metadata/log/binary SHA-256；primary 和 verification source commit/head/tag_commit；两边 tool path/version/SHA-256；recipe ID、`semantic_environment`、`semantic_argv`、source epoch 和 jobs；verification binary SHA-256；comparison；runtime binary SHA-256 和 parsed Redis version；cleanup booleans；platform os/kernel/architecture；limitations。Raw `INFO server` hash、timestamp、临时绝对 path、HOME/TMPDIR、`executed_argv`/`executed_environment` 中的 FD number、inode/device/nlink、verification log hash 和 WSL 调度字段不属于跨运行 stable projection，但仍分别满足 schema、identity、大小和顺序约束。
10. 任一缺字段、未知字段、duplicate key、hash mismatch、identity drift、schema mismatch、大小超限或跨字段不变量失败都必须 fail closed。

## 12. PowerShell 入口

PowerShell wrapper 只承担 Windows 参数安全和 WSL 调度：

- 不在 Windows 原生环境伪造 Linux evidence；
- 明确选择 WSL distro；
- Windows path 通过受控 `wslpath` 转换；
- 在 WSL 内直接调用 production shell verifier；
- output 预检查在进入 WSL 前和 shell verifier 内各执行一次；
- 默认 Windows test 对 Linux-only 场景使用带原因静态 ignore；显式 `--include-ignored` 才运行完整 WSL E2E。

PowerShell wrapper 不降低 shell verifier 的 independent rebuild、hash equality 或 cleanup gate。

## 13. 测试策略

### 13.1 必须先红的安全回归

- exact clean real Git source + ignored fake `redis-server` + 完全自洽 metadata/log 必须在 fake binary 启动前被拒绝；
- metadata-selected Python/Git/CC/Make 不得被执行；
- ambient fake `python3`、fake `realpath`、恶意 `PYTHONPATH` 不得接管 controller；
- held Make 探测后替换路径，真正 build 仍绑定 held FD或明确失败；
- local Git config helper 无限输出、挂起、忽略 TERM/派生 child 时必须有界并回收；
- verification checkout build hash mismatch 必须不启动 runtime、不发布 provenance；
- runtime/checkout/verification-log cleanup、fallible evidence handle close，或 primary evidence、source A、tool FDs、output parent 最终复核失败必须不发布 provenance。

### 13.2 快速闭环

测试 controller 使用真实 production scripts 的受控副本和 fake Git/CC/Make/Redis fixture，覆盖 schema、命令、FD binding、process cleanup 和 publication order。测试不能手写一份与 production build schema 平行的 success metadata 来替代 build-to-verify 闭环。

### 13.3 真实 WSL/Linux 门禁

必须从官方 exact Redis 8.8.1 clone 执行：

```text
primary build
  → shell verifier fresh clone + independent rebuild
  → binary hash equality
  → runtime INFO from rebuild
  → PowerShell wrapper verifier with separate output
```

两个 provenance output 不得覆盖；JSON 必须严格解析并逐字段交叉核对。Linux-native Rust manifest suite、Windows default suite、Windows+WSL explicit suite、Clippy、format、shell syntax、PowerShell parser 和 Git diff checks 均是提交前门禁。

## 14. 性能与运行成本

方案 A 会把正式 Oracle 验证的 Redis 构建成本提高到两次。该成本只发生在兼容证据生成、CI/release gate 或显式 Oracle refresh，不进入 Kiwi 请求路径。

未来只有经单独 Decision 批准并纳入 versioned recipe 后，才允许通过编译缓存减少墙钟时间。届时 cache key 必须绑定 exact source、controller、toolchain、argv 和 environment；cache hit 不能跳过 verification binary hash、runtime identity 和 provenance 发布门禁。
